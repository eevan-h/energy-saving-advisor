# 節能改善示範推薦維護說明

前台顯示已簡化：規則分數與明細仍在本文件及規則程式內追溯，不再出現在推薦結果；權重與排序未變。來源與審核資料獨立保存於 `src/data/measureReviews.ts`，技術依據僅供內部管理，詳見[公開與內部資料維護](technical-evidence-maintenance.md)。

目前規則版本為 `demo-rules-v2`。本版只使用本機 TypeScript 規則，不呼叫 AI API，不估算節電率、節省金額或回收年限。

**規則匹配分數**僅表示回答與示範措施的匹配程度及排序依據，並非節能率、節省金額或投資報酬率，也不代表專業診斷。畫面會在每張措施卡片明確標示分數，並提供規則明細。

## 檔案分工

- `src/data/measures.ts`：13 項措施、設備專屬 `selectionReason`、具體建議、投資及來源審核資料。
- `src/lib/recommendations.ts`：設備篩選、問題相關性權重、分數、固定順位、回答證據與規則版本。
- `src/components/Recommendations.tsx`：推薦理由、規則匹配分數及可展開的明細；從目前回答重新推導結果。
- `tests/recommendations.test.ts`：設備情境、未知狀態、理由證據、排序及審核標示驗證。

## 設備專屬理由及證據界線

| 類別 | 理由的判斷重點 | 不可直接推定的情形 |
| --- | --- | --- |
| 空調 | 冷房需求、實際使用時段、個別年限與維護紀錄 | 冷房不佳不等於排程錯誤或必須汰換 |
| 照明 | 營業時段、無人區域、作業所需照明與燈具狀態 | 照明老舊不等於無人時仍開燈或照度不足 |
| 冷凍冷藏 | 保存溫度、持續運轉需求、開門與散熱管理 | 長時數不等於已確認全天運轉；不建議為節能任意停機 |
| 空壓 | 洩漏查核、供氣壓力、用氣時段與製程需求 | 未量測不能宣稱已有洩漏或壓力過高 |
| 一般用電管理 | 非營業時間必要用電清單、巡查責任與定期檢視制度 | 未詢問現行制度，不能判定有管理缺失或非營業時間浪費 |

既有問答沒有詢問確切營業時間、無人區域、實測溫度、供氣壓力或管理制度。這些內容只能作為「先核對／可檢查」的方向，不得寫成使用者已確認的事實。

`RuleReason.evidence` 保存本項判斷實際引用的回答欄位與值；設備專屬理由只引用清單中對應的設備，不在每項理由重複整份設備清單。未知資料以單一理由合併呈現，不重複逐欄加分。與本措施有關的未知時數或年限，可用零分的保守查核理由說明。

`showInReasons` 控制是否出現在主要推薦理由；分數明細始終保留全部規則。基準分與投資調整不是回答判斷，`evidence` 為空，不偽裝成設備或場所回答。一般管理只有在沒有其他觸發理由時，才顯示基礎的保守管理說明。

## 篩選及權重

必須完成五題才產生推薦。設備專屬措施僅限已選設備，不依場所猜測設備存在。一般用電管理適用全場所。只選「其他」時先推薦設備盤點。場所資料保留供頁面顯示與未來有依據的擴充，目前不作為理由或加分條件。

更新設備評估僅在年限為「6～10年」或「超過10年」時納入；照明亦可由明確的「照明設備老舊」回答觸發。這是評估入口，不代表已判定應汰換。整體設備年限及時數不等於每台設備的實測資料。

| 規則 | 規則匹配分數加減 |
| --- | --- |
| 已選設備 | +40 |
| 冷房問題：空調檢測／更新評估／時段管理 | +60／+35／+20 |
| 照明老舊：檢測／更新評估／開關管理 | +50／+55／不加分 |
| 設備耗電量高：設備專屬檢測／運轉管理 | +30／+10 |
| 年限 6～10 年／超過 10 年：檢測／更新評估 | +25／+20 |
| 每日 9～12 小時／超過 12 小時：空調運轉管理 | +25 |
| 每日 9～12 小時／超過 12 小時：照明開關管理 | +20 |
| 每日 9～12 小時／超過 12 小時：冷凍冷藏溫度管理 | +35 |
| 每日 9～12 小時／超過 12 小時：空壓供氣管理 | +30 |
| 每日 9～12 小時／超過 12 小時：一般用電管理 | +10 |
| 一般管理起始分 | +10 |
| 一般管理：電費偏高／不知道從何開始 | +25／+35 |
| 月費 10001～30000 元／30001 元以上：帳單盤點 | +15 |
| 未知資料需補齊：一般管理，只計一次 | +20 |
| 僅選其他或問題與設備清單不一致：一般管理 | +25（兩條件不重複計分） |
| 設備專屬的相關年限或時數未知：保守提醒 | 0 |
| 需要設備投資 | -10 |

「不清楚」不觸發高電費、老舊或長時數條件。較高電費級距不代表浪費；改善問題與設備清單不一致時，引用這兩項實際回答提示確認，不引入未選設備。

冷房不佳的原因查核優先於僅核對時段；照明老舊優先連結檢測及更新，不替開關時段管理加分。「設備耗電量高」是整體問題，僅提高已選設備的檢測及次要運轉查核順序，不直接判定其中任何設備耗電異常。

## 固定排序與追溯

1. 規則匹配分數由高至低。
2. 同分比較設備投資：不需新增設備、視檢測結果評估、需要設備投資。
3. 再比較措施類型：檢測、運轉管理、更新評估、一般管理。
4. 再比較固定設備類別：空調、照明、冷凍冷藏、空壓、一般用電管理。
5. 最後按措施編號的字元順序比較，不使用受語系影響的字串排序。

同分排序是固定呈現約定，不代表某設備有較高節能效益。目錄順序與設備勾選順序不改變排序。

80 分以上為「優先檢視」、50～79 分為「接續安排」、其餘為「後續評估」。這些層級與權重是本專案示範規則，不是官方標準。每個加減分保留規則編號、實際回答證據、說明與規則版本，總分必須等於規則分數加總。

## 未來匯入手冊

`Measure` 是目錄資料契約，新增措施時需填入設備專屬 `selectionReason`。`recommend(place, answers, catalog)` 可接受整理後的措施目錄，無須修改畫面；目前未建立實際匯入器。新增設備或判斷條件需同步更新權重、理由及測試，不可將未詢問的情形直接當成已知資料。

`relevantPlaces` 保留為目錄情境資料，目前不參與排序；`matchingProblems` 仍須配合規則中的設備與措施類型判斷，不會單靠清單就為無關措施加分。

日後對照手冊時，將原始標題、出版單位、原始 URL、章節／頁碼、核對日期及核對者填入 `source.kind = 'manual'`；內容經專業審核後才可將 `reviewStatus` 改成 `reviewed`。這些欄位僅保存人工核對紀錄，不代表系統會自動驗證來源真偽。缺少紀錄或仍為示範來源時，維持「示範建議，待專業審核」。

本版五類、13 項措施全部為內建示範內容，未引用或宣稱核對任何官方來源。

## 驗證

於專案目錄執行 `npm.cmd test` 及 `npm.cmd run build`。測試保留原五種指定情境，新增設備理由關鍵判斷、問題相關性差異、引用與回答一致、未知狀態合併、場所不加分、同分排序及分數免責說明驗證。

答案只存在當次操作的 React 狀態；返回修改會保留，重新整理頁面會重置。
